# ADR 0001. Выбор SQLite в качестве базы данных

- **Статус:** принято.
- **Дата:** начало проекта.

## Контекст

Сервис хранит активности, расписания и брони. Нагрузка низкая: один
организатор и его гости в день, не тысячи запросов в секунду. Студенты
курса запускают проект у себя на ноутбуке, иногда в контейнере. Нужна база,
которая:

- ставится одной командой вместе с проектом, без отдельного сервера;
- работает в Docker без отдельной настройки;
- доступна из TypeScript без сложного асинхронного слоя;
- переживает перезапуск процесса (демонстрационные данные не должны
  исчезать).

## Решение

Используем SQLite через драйвер `better-sqlite3`. Файл базы — `booking.db`
в корне проекта.

`better-sqlite3` выбран потому, что это **синхронный** драйвер: результат
запроса приходит сразу, не нужен `await` на каждом обращении к базе.
Бизнес-логика остаётся линейной и читается с первого прохода.

Все SQL-запросы собраны в `server/src/repository.ts`. В обработчиках
маршрутов SQL нет. Схема таблиц описана в `server/src/db.ts` и применяется
при старте. Это разделение явно зафиксировано в `AGENTS.md`.

## Последствия

**Становится проще**

- Один файл вместо сервера БД. Бэкап — это копия файла.
- `npm install` поднимает всё, включая базу. Студенту не нужно ставить
  отдельный сервер СУБД.
- В тестах каждый сценарий получает чистую базу простым удалением файла.
- Синхронный API делает код линейным и не прячет управление потоком за
  `await`.

**Становится сложнее**

- Не масштабируется на несколько машин. Это сознательное ограничение для
  учебного проекта.
- Все записи сериализуются одной блокировкой. Для нашего объёма это
  незаметно; под нагрузкой тысяч записей в секунду SQLite станет узким
  местом.
- Нет сетевого доступа к базе. Если бы сервис был распределённый, это
  было бы проблемой.

## Альтернативы

- **PostgreSQL.** Мощнее, поддерживает сетевой доступ, развитый набор
  индексов. Но требует отдельной установки и отдельной миграции при
  развёртывании, добавляет слой инфраструктуры. Для учебного проекта это
  лишняя сложность без выигрыша. Прямой запрет на замену SQLite зафиксирован
  в `AGENTS.md`.
- **JSON-файл на диске.** Ещё проще, но нет транзакций. При двух
  одновременных записях файл можно повредить, а конкурентный доступ
  небезопасен.
- **In-memory хранилище (Map).** Самое простое из возможного, но
  состояние теряется при перезапуске. Демонстрационные данные не должны
  исчезать, поэтому этот вариант не подходит.

## Когда пересматривать

- Если сервис потребуется запустить в нескольких экземплярах за балансировщиком.
- Если число активных броней перевалит за десятки тысяч в день и
  сериализация записей станет узким местом.
- Если появится необходимость в репликации для отказоустойчивости.
