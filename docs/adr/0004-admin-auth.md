# ADR 0004. Аутентификация администратора

- **Статус:** принято.
- **Дата:** после `PDR-0001` и `ADR-0001…0003`.

## Контекст

Сервис сознательно не делал учётных записей и паролей для гостей
(`PDR-0001`, раздел «Не делаем»): гость попадает на страницу по прямой
ссылке и опознаётся адресом почты при бронировании. Это работает для
массового сценария, но не закрывает админскую задачу: организатор должен
видеть, кто записался, и при необходимости отменять брони. Хранить
список гостей в открытом доступе нельзя — это утечка персональных
данных. Значит, нужен режим, доступный только администратору.

В этой версии не делается полноценная система ролей и приглашений
(см. PDR-0001, «Что осознанно не делается»): единственный
администратор — тот, кто разворачивает сервис.

## Решение

Один логин и пароль хранятся в переменных окружения и проверяются
на сервере. Сессия — `httpOnly` cookie с подписью через
`node:crypto.createHmac('sha256', secret)`. Поверх — простой
брутфорс-лимит на 5 попыток в минуту с одного IP.

### Логин и пароль

`BOOKING_ADMIN_LOGIN` и `BOOKING_ADMIN_PASSWORD` — необязательные
переменные. Если не заданы, используются dev-значения `admin` и
`Pas!_123`, и в лог печатается предупреждение. Это осознанное
упрощение: для прода нужно задать пару через `docker-compose.yml`
или переменные окружения процесса.

Пароль **не хранится** в БД и **не хранится** в памяти процесса в
открытом виде. При старте сервер считает хеш через `bcryptjs` с
`saltRounds = 10` и кладёт его в замыкание. Сравнение — через
`bcryptjs.compareSync`. Это даёт устойчивость к атаке по
утечке памяти процесса: хеш бесполезен без оригинала.

### Сессия

`POST /api/admin/login` при успехе ставит cookie `admin_session` с
форматом `login.expiry.sig`, где:

- `login` — идентификатор администратора;
- `expiry` — момент истечения в формате `unix seconds`;
- `sig` — `hex(hmacSha256(secret, "login|expiry"))`.

Cookie отдаётся с флагами `HttpOnly; SameSite=Lax; Path=/; Max-Age=28800`
(8 часов). Секрет берётся из `BOOKING_SESSION_SECRET` или генерируется
случайно при старте (с предупреждением в лог). В проде `BOOKING_SESSION_SECRET`
обязателен — иначе при рестарте все сессии инвалидируются.

Подпись сравнивается через `timingSafeEqual`, чтобы время ответа
не утекало в сигнал для подбора.

### Брутфорс

`Map<ip, { attempts, resetAt }>` в памяти процесса: 5 неудачных
попыток в минуту с одного IP — шестая и далее отвергаются
с `attempts_left: 0`. Хранится в памяти: при рестарте сбрасывается.
Для учебного проекта это нормально.

### API

| Метод  | Путь                              | Доступ     | Описание                    |
| ------ | --------------------------------- | ---------- | --------------------------- |
| `POST` | `/api/admin/login`                | без cookie | вход, ставит cookie         |
| `POST` | `/api/admin/logout`               | любая      | очищает cookie              |
| `GET`  | `/api/admin/me`                   | любая      | `logged_in: boolean`        |
| `GET`  | `/api/admin/bookings`             | админ      | все брони с `activity_name` |
| `GET`  | `/api/admin/activities`           | админ      | все активности              |
| `GET`  | `/api/admin/schedules`            | админ      | все расписания              |
| `POST` | `/api/admin/bookings/{id}/cancel` | админ      | отмена любой брони          |

Код ошибки один: `unauthorized: 401`. Он покрывает все случаи
(нет cookie, неверный пароль, истёкшая сессия, превышен лимит).
В ответе `/login` есть необязательное поле `attempts_left` — оно
нужно UI, чтобы показывать «осталось N попыток» в модалке.

## Последствия

**Становится проще**

- Один логин, одна роль, простая модель: есть cookie — админ,
  нет — гость. Никаких ролей, никаких «роль админа в БД», никаких
  приглашений.
- Хеш в замыкании не торчит в БД и не светится в логах.
- Брутфорс-лимит защищает от перебора даже при слабом dev-пароле.
- Тесты `server/tests/unit/adminAuth.test.ts` покрывают подпись,
  проверку и счётчик попыток без БД.

**Становится сложнее**

- Зависимость `bcryptjs@2.4.3` — нарушает «не добавлять зависимости
  без явной необходимости» (`AGENTS.md` §10). Решение осознанное
  и зафиксировано здесь.
- Состояние счётчика попыток и сгенерированный секрет теряются
  при рестарте. Для прода это закрывается `BOOKING_SESSION_SECRET`
  и внешним rate-limiter, если потребуется.
- CORS теперь с `credentials: true` — фронт в dev-режиме
  отправляет cookie через Vite-прокси.

## Альтернативы

- **JWT.** Даёт stateless-сессии и готовую ротацию ключей. Сложнее
  в реализации и не даёт выигрыша для одного админа.
- **Сессии в БД.** Позволяют мгновенно отзывать сессии. Для
  одного пользователя это лишняя инфраструктура.
- **Несколько админов с ролями.** Не входит в задачу этой версии
  (см. PDR-0001). Если потребуется, проще будет сразу
  переехать на JWT или на полноценный IdP.
- **`scrypt` из `node:crypto` вместо `bcryptjs`.** Убирает
  зависимость, но требует аккуратной работы с `salt` и параметрами
  вручную. `bcryptjs` проще для учебного проекта.

## Когда пересматривать

- Если потребуется больше одного администратора.
- Если сессии начнут храниться в БД, чтобы отзывать их мгновенно.
- Если производительность `bcryptjs.compareSync` станет узким местом
  (для одного логина — крайне маловероятно).
